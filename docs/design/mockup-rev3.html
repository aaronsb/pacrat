pacrat — flow & screens

A curation TUI for Arch packages: browse the repos and the AUR, vendor what you trust into the dotfiles store, collect gradings from any configured analyzer, and serve every machine from a repo you control — so yay just works.

  • pacrat manifest · vendored trees · gradings · decisions
  • yay-friend one grader behind the contract
  • aurutils fetch · build · local repo
  • dotfiles store synced shared state
  • pacman/yay/update-arch unchanged

1 · The two loops

Everything the UI does serves one of two loops. The custody ladder is how a package moves into your control; the update loop is what happens, forever after, to everything on the vendored rung and above.

custody ladder

  • unmanaged Installed on some host; invisible to the manifest. Browsable with full metadata like everything else.
  • adopt · A tracked In the manifest with host/profile membership. Still updates from its upstream repo; upstream drift is flagged.
  • vendor · v vendored PKGBUILD tree committed to the store at a reviewed commit. Built into [dotfiles-aur]; the AUR is no longer consulted by pacman/yay.
  • claim maintained Yours. Same as vendored, plus push rights back to the AUR.

Moving down the ladder is always allowed (drop returns a package to the rung below). Official-repo packages top out at tracked — vendoring is an AUR-package concept.

update loop (vendored & maintained)

  • current Store tree == reviewed commit; built package served.
  • drift check drifted Upstream moved past the reviewed commit — an update available to adopt.
  • graders run graded Configured graders score the candidate commit; pacrat maps the grade to PROCEED / WARN / BLOCK with its own thresholds (§9).
  • decide gate adopted Auto, semi-auto, or manual (§8). BLOCK holds regardless of mode.
  • makepkg + repo-add served Built into [dotfiles-aur]; reviewed commit advances; every host picks it up on next -Syu.

The verdict is pacrat's data: graders return numbers and findings, pacrat owns thresholds, decisions, and history. A held package simply never gets a new build — yay keeps serving the last approved version, no flag files, no pinning tricks.

2 · Screen model

One binary, two faces. Bare pacrat opens whatever default_ui says in ~/.config/pacrat/config.toml; any subcommand is always CLI. Six screens on number keys; every action a screen offers has a CLI twin (§11).

keyscreenquestion it answers
1overviewwhat needs my attention?
2browsewhat exists, and what's our relationship to it?
3updateswhat changed upstream, and what did the graders say?
4hostsdoes each machine match the manifest?
5jobswhat is pacrat running right now, exactly?
6configwhich gates are auto, and what's connected?

Global keys: j/k move · / filter · enter detail · ? help · q back/quit.

Scrolling and paging are first-class everywhere. Every list and pane scrolls independently: j/k line, ctrl-d/ctrl-u half-page, ctrl-f/ctrl-b (or PgUp/PgDn) full page, g/G top/bottom. tab moves focus between a screen's regions and the focused region is the one that scrolls, marked by an accent border. Any region with overflow shows a scrollbar plus a 12/214 position indicator — with 200+ tracked packages and multi-hundred-line PKGBUILD diffs, no list is ever assumed to fit. (ratatui's Scrollbar widget and list state make this cheap; the discipline is designing every region as a viewport from day one.)

Diff and grading share the screen because that's the actual decision: "what changed" beside "what the graders think of it" — with the exact grader invocation shown, never hidden. The upstream region flags updates for tracked-but-not-vendored AUR packages: they'd otherwise update outside your control, so pacrat surfaces them and offers vendoring at the new version. Selecting the BLOCK row shows why — e.g. post_install() gained curl … | sh, the June-incident pattern — and offers no adopt key at all: held updates can only be rejected, deferred, or escalated to the full report.

The pipeline is drawn, and the preset selects gate modes. Each gate is auto (proceed silently), verbose (proceed, narrating), or manual (stop and ask). Presets are just bundles — enter on a gate overrides it individually. Two invariants no preset can change: BLOCK always holds, and every grader/build call is logged in jobs. The sources region is the connection status for everything pacrat talks to.

9 · The grading contract

PROCEED/WARN/BLOCK is pacrat's data. Graders — yay-friend, some future tool, or you by hand — only return a number and findings, through one convention: pacrat-grade/v1. pacrat invokes each configured grader with the candidate tree and commit, and expects contract JSON on stdout:

$ yay-friend analyze mdcat --format pacrat --commit 7d02e4c
{
  "contract": "pacrat-grade/v1",
  "grader":   "yay-friend",
  "subject":  { "package": "mdcat", "commit": "7d02e4c", "version": "2.11.0-1" },
  "grade":    0,
  "scale":    { "min": 0, "max": 4 },
  "findings": [
    { "level": 0, "title": "version bump only", "span": "PKGBUILD:3" }
  ],
  "meta":     { "provider": "claude", "duration_s": 41, "cached": true }
}
  • pacrat owns the verdict. Grade → PROCEED/WARN/BLOCK happens in pacrat via its thresholds, never in the grader. Changing your risk posture is a config edit, not a grader release.
  • Cache key is (grader, package, commit). A grading is valid for exactly one candidate commit; if upstream moves again, pacrat re-dispatches instead of reusing. yay-friend already caches by commit hash, so it's naturally idempotent — the adapter is thin: an output format, not a redesign.
  • Failure is ungraded, and ungraded is not PROCEED. A grader that exits non-zero, times out, or emits invalid JSON leaves the package ungraded; in auto mode ungraded holds, same as WARN.
  • Manual grading is a first-class grader. pacrat grade mdcat --grade 0 --note "read it myself" records a human verdict for that commit, alongside — not instead of — tool gradings.
  • Multiple graders: worst grade wins (proposed — open question 5).
  • Every invocation is visible in jobs, argv verbatim, with duration and cached/fresh status.

10 · One-shot mode & guard rails

The whole update loop runs headless as a single command — detect everything, grade everything, decide by policy, build what passed. This is the same engine as screen [3], with every gate on auto; run it from a timer and the repo is always current before any -Syu:

$ pacrat update --mode auto
detect   5 upstream updates (4 vendored · 1 tracked)
grade    yay-friend: 4 cached · 1 fresh (lug-helper @ e91ab77 · 38s)
decide   4 adopt · 1 hold
  hold   obsbot-camera-control 1.3.1   grade 4 → BLOCK  (post_install curl|sh)
build    4 built → [dotfiles-aur] · repo db updated
exit     10 (holds present — pacrat updates to review · --format json for machines)

Nothing else on the system needs to know pacrat exists. update-arch, yay -Syu, plain pacman — all unchanged: vendored packages resolve from [dotfiles-aur], and a held package simply has no new build, so hosts keep the last approved version with zero pinning. What pacrat does own are the guard rails — the pacman hook and yay config it deploys (config screen, §8) so a brain-fart can't bypass the managed repo:

$ yay -S some-shiny-aur-thing
:: pacrat guard — some-shiny-aur-thing would install from the AUR directly,
   bypassing [dotfiles-aur]. Bring it through curation instead:
     pacrat vendor some-shiny-aur-thing
   override once: PACRAT_BYPASS=1 yay -S some-shiny-aur-thing (logged)
error: failed to commit transaction

Mechanism: a PreTransaction pacman hook (deployed by pacrat setup) aborts installs of foreign packages that didn't come through pacrat — pacrat's own builds set an env marker the hook recognizes. yay stays fully usable for everything sanctioned; the only path it can't take is the one around the curation flow, and even that has a logged, deliberate escape hatch.

13 · Open questions for ADR-001

  1. Bulk adopt ergonomics. 43 unmanaged packages won't be adopted one at a time. Multi-select in hosts is the sketch; is there also an "adopt everything currently installed, then prune" first-run mode?
  2. Block override policy. No UI path approves a BLOCK. Should a CLI-only escape hatch exist (pacrat adopt-update --override-block --reason "…", recorded in sources.toml), or is rejection + manual vendoring the only path?
  3. Jobs runtime. One-shot mode covers timers and update-arch; inside the TUI, do jobs run only while pacrat is open, or does a user service own the queue?
  4. Sync transport. Hosts screen shows remote sync over ssh — or does each host only ever sync itself, with the matrix as read-only awareness for the others?
  5. Multi-grader aggregation. Worst-grade-wins is the proposal; do graders ever get weights or veto scopes (e.g. manual overrides tools)?
